# YCFMG 架构设计

> 版本：fmg2609.001 ｜ 定位：文件管理 × 智能图库的单体可执行应用

## 1. 设计目标与取舍

传统文件管理器与图库是两种割裂的形态：前者路径自由但检索弱，后者检索好但必须「导入库」。
YCFMG 的核心决策是 **不为检索而搬迁文件**：文件永远留在真实目录里，图库只是对同一批文件的一层
「索引视图」。因此系统里只有一个事实来源（文件系统），数据库只存派生的可重建数据。

由此推导出的三条架构约束：

1. **数据库可丢弃**：删除 `ycfmg.db` 后重新索引即可完全恢复，不承载任何原始数据。
2. **零外部依赖可运行**：默认不依赖任何 AI 模型、向量库、消息队列；以图搜图与以文搜图均由本地算法完成。
3. **单一二进制**：前端资源通过 `go:embed` 打进可执行文件，部署时只有一个文件。

## 2. 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│  表现层  web/  （原生 HTML/CSS/JS，嵌入二进制，无构建步骤）      │
│  资源管理器视图 ── 图库视图 ── 分享管理 ── 设置 ── 专属分享页      │
├──────────────────────────────────────────────────────────────┤
│  接口层  internal/server/  net/http 路由、中间件、JSON 契约      │
├──────────────────────────────────────────────────────────────┤
│  业务层                                                        │
│  fsapi 文件操作 │ indexer 索引 │ search 检索 │ share 分享        │
│  auth 账号会话  │ media 流式传输 │ thumbs 缩略图                  │
├──────────────────────────────────────────────────────────────┤
│  能力层  vision/  感知哈希、颜色直方图、EXIF 解析、规则分类        │
├──────────────────────────────────────────────────────────────┤
│  存储层  store/  SQLite（纯 Go 驱动，无 cgo）                    │
└──────────────────────────────────────────────────────────────┘
```

模块依赖是单向的：`server → {fsapi, search, share, auth, media, indexer} → {store, vision} → {util, config, logx}`。
`vision` 不依赖 `store`，因此特征提取可以单独测试与复用。

## 3. 数据模型

| 表 | 作用 | 是否可重建 |
| --- | --- | --- |
| `files` | 文件与图像特征主表（路径唯一） | 是（重新索引） |
| `dirs` | 目录统计与封面缓存 | 是 |
| `tags` / `file_tags` | 标签体系（自动标签 + 手动标签） | 是 |
| `shares` / `share_visits` | 分享记录与访问日志 | 否（用户数据） |
| `users` / `sessions` | 账号与会话 | 否 |
| `settings` | 运行时覆盖项（多域名、品牌名等） | 否 |
| `scan_jobs` | 索引任务历史 | 是 |
| `embeddings` | 可选语义向量（配置 CLIP 端点后才有值） | 是 |

`files` 表的关键特征列：

- `hash_a` / `hash_d` / `hash_p`：均值哈希、差值哈希、DCT 感知哈希（64 位，以 int64 存储位模式）
- `hist`：4×4×4 颜色直方图（64 字节，归一化到 0..255）
- `color`：主色 `#RRGGBB`；`aspect` / `bright` / `sharp`：画幅、亮度、清晰度
- `classify`：规则分类结果；`tags`：自动标签（逗号分隔，便于 SQL LIKE 粗筛）
- `quick_hash`：头尾各 64KB + 文件大小的 SHA256，用于秒级判重

## 4. 检索设计

系统提供三条互补的检索路径，按可用性自动降级：

### 4.1 以图搜图（默认可用，无模型依赖）

1. 对查询图计算 aHash / dHash / pHash 与颜色直方图；
2. 遍历索引中的图像特征（流式读取，不整表载入内存）；
3. 融合打分：`0.45·pH 相似 + 0.30·dHash + 0.10·aHash + 0.15·直方图`；
4. 若 `pHash 汉明距离 ≤ 容差` 且 `直方图 L1 < 0.35`，标记为「疑似重复」。

复杂度 O(N)，10 万张图片量级下单次检索为百毫秒级，无需向量库。

### 4.2 以文搜图（默认可用，中文友好）

1. 分词：中文按单字 + 二元组切分，英文/数字按词切分，过滤停用词；
2. 同义词扩展：内置 50+ 组中文语义词典（「猫 → 猫/猫咪/cat/kitty」）；
3. SQL 粗筛：对扩展词做多字段 `LIKE` 召回，把候选集压到千级；
4. 字段加权打分：标签 3.5 > 文件名 3.0 > 分类 2.5 > 目录 1.2 > 相机 1.0，叠加完整短语与收藏加成。

### 4.3 语义增强（可选）

配置任意 OpenAI 兼容的 `/v1/embeddings` 端点后，可对图片写入向量并做余弦检索；
未配置时该路径整体关闭，不影响前两条路径。

## 5. 分享与多域名

分享的核心问题是「链接该用哪个域名」。设计如下：

```
请求进入 → 解析 Host（trust_proxy 时取 X-Forwarded-Host）
         ├─ 命中 public_urls 中的域名 → 该域名排首位
         └─ 未命中 → 当前 Host 动态生成一个域名并排首位
         → /api/shares/{id}/links 返回全部可用链接并标注 primary / current
```

这样同一份分享在任何入口域名下访问，复制出来的链接都是「用户当前正在用的域名」，
同时后台仍能看到全部绑定域名与访问来源。分享页 `/s/{token}` 由服务端渲染，
不依赖前端框架，密码保护通过 HMAC 签名 Cookie 实现（有效期内免重复输入）。

## 6. 索引流水线

```
定时器 / 手动触发 / 浏览目录时按需触发
   ↓
WalkDir（跳过 exclude 名单：.@__thumb、#recycle、@eaDir 等）
   ↓ 每个文件：stat 比对 size+mtime，未变化则跳过（增量）
   ↓ 图片：读 EXIF → 计算哈希/直方图/颜色/清晰度 → 规则分类 → 生成自动标签
   ↓ 批量 128 条一个事务写入 SQLite
   ↓ 目录级：写入 dirs 统计（文件数/图片数）
   ↓ 收尾：标记磁盘上已消失的记录为 missing，重建标签计数
```

## 7. 安全边界

- **路径穿越防护**：所有文件 API 必须经过 `fsapi.Guard`，路径必须落在受管文件库内（`util.WithinBase`）。
- **写权限双重校验**：全局只读开关 + 单个文件库只读标记。
- **分享越权防护**：分享下载/缩略图接口校验请求路径必须属于该分享的条目（含目录前缀），而非任意路径。
- **会话**：bcrypt 存密码哈希，会话落库支持过期与主动注销，Cookie 为 HttpOnly + SameSite=Lax。
- **回收站**：默认删除只是移动到数据目录下的回收站并记录原路径元数据，可恢复。

## 8. 关键取舍记录

| 决策 | 备选 | 理由 |
| --- | --- | --- |
| Go 单二进制 | Node/Python 应用 | NAS 上无需运行时，fpk/容器体积与启动速度最优 |
| 纯 Go SQLite | cgo 版 sqlite3 | 交叉编译无工具链依赖，静态链接 |
| 感知哈希 + 直方图 | 内置 CLIP 模型 | 模型体积与内存对 NAS 不友好；哈希方案零依赖、可解释 |
| 前端无构建 | Vue/React + Vite | 仓库可 `git clone` 后直接 `go build`，无 Node 工具链要求 |
| 服务端渲染分享页 | SPA 路由 | 分享链接要能被任何浏览器/爬虫直接打开，且需极简首屏 |
| 规则分类 | 训练模型 | 分类项可读、可调、可解释，用户能自行增补关键词 |
